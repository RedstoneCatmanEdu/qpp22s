# QPP22S (QUIC Ping Pong to 2 Servers)

Данный репозиторий содержит учебный проект, реализующий тестовое задание: разработку QUIC-aware балансировщика нагрузки на базе Open vSwitch и OS-Ken согласно `Pj.pdf`.

## Архитектура и функционал

Проект реализует SDN-балансировщик для QUIC-соединений. Он распределяет новые соединения между двумя серверами по алгоритму Round Robin и сохраняет привязку клиента к серверу, даже если IP-адрес или UDP-порт клиента изменяются (NAT Rebinding).

Структура проекта:
* `controler/` — исходный код контроллера OS-Ken (Python).
* `src/` — исходный код QUIC-серверов и клиентов (Go).
* `scripts/` — скрипты автоматизации сборки и запуска.
* `tests/` — автоматические тесты (Bash и pytest).
* `topo.py` — скрипт создания топологии для Mininet.

## Сетевая топология

```text
QUIC Client (192.168.10.10)
      |
      v
Open vSwitch (VIP: 192.168.10.100)
      |
      |--- Server 1 (10.0.0.11)
      |
      |--- Server 2 (10.0.0.12)
```

## Формат Connection ID (CID)

Для stateless-маршрутизации сервер кодирует свой ID прямо в Connection ID. Длина CID фиксирована — 12 байт.

```text
+------------------+-----------+---------------------+

| Configuration ID | Server ID |     Random Data     |
|     1 byte       |  1 byte   |       10 bytes      |
|      (0xA1)      |  (1 or 2) |                     |
+------------------+-----------+---------------------+
```

* Пример CID для Сервера 1: `A1014B829157304C71A8B92D`
* Пример CID для Сервера 2: `A1029C1742F5186394AB7721`

## Установка и сборка

1. Установите системные зависимости (Open vSwitch, Mininet и компилятор Go)

например с помощью `dnf`:
```bash
sudo dnf install openvswitch mininet golang
```

2. Запустите скрипт автоматической настройки. Он установит необходимые Python-библиотеки (OS-Ken, pytest) и скомпилирует Go-бинарники в папку `bin/`.

## Запуск проекта

Для запуска используются скрипты из папки `scripts/`.

1. Запуск контроллера, Mininet и серверов:
```bash
./scripts/run.sh
```
После выполнения вы окажетесь внутри консоли Mininet. Контроллер будет записывать логи в фаил `logs/controler.log`.

2. Запустите клиент внутри Mininet (примеры команд):

* 1 запрос (микроклиент):
```mininet> 
client ./bin/microclient -addr 192.168.10.100 -port 443
```

* 1 клиент:
```mininet> 
client ./bin/client -addr 192.168.10.100 -port 443 -c 1
```

* 10 клиентов (с одного IP, но с разных исходных портов):
```mininet> 
client ./bin/client -addr 192.168.10.100 -port 443 -c 10
```

* Клиент, меняющий свой порт во время работы (имитация NAT Rebinding):
```mininet> 
client ./bin/client -addr 192.168.10.100 -port 443 -ChangePort
```

### Альтернативный запуск (вместо `scripts/run.sh`)

Если вам требуется более тонкая настройка, компоненты можно развернуть вручную в отдельных терминалах:

1. Запустите эмуляцию топологии:
```bash
sudo python3 topo.py
```

2. Запустите контроллер нагрузки в отдельном терминале. Вы можете задать время жизни правил с помощью флага `-t` / `--idle-timeout`:
```bash
python3 controler/run_controler.py -t 40
```

3. Запустите серверы внутри консоли Mininet:
```text
mininet> server1 ./bin/server -id 3 &
mininet> server2 ./bin/server -id 4 &
```

## Пример OpenFlow-правил

При поступлении трафика, например от клиентов:
```text
mininet> client ./bin/client -addr 192.168.10.100 -port 443 -c 10
```
Контроллер устанавливает правила для DNAT (клиент -> сервер) и SNAT (сервер -> клиент).

Пример правила для входящего трафика (Client -> VIP):
```text
Match: in_port=1, eth_type=0x0800, ip_proto=17, ipv4_src=192.168.10.10, ipv4_dst=192.168.10.100, udp_src=xxxx, udp_dst=443
Actions: set_field(eth_dst=00:00:00:00:00:11), set_field(ipv4_dst=10.0.0.11), output:2
```
*Примечание: время жизни правил (`idle_timeout`) по умолчанию составляет 60 секунд, но его можно изменить при запуске контроллера.*

## Тестирование

Все системные (интеграционные) тесты можно запустить одной командой:
```bash
./tests/test_all.sh
```

Ниже приведено соответствие тестовых скриптов сценариям, описанным в задании (`Pj.pdf`):

* **`tests/test1.sh`** — реализует **Тест 1 (Установление QUIC-соединения)**. Запускает микроклиента через VIP и проверяет, что контроллер установил правила, а клиент успешно получил ответ от сервера.
* **`tests/test2.sh`** — реализует **Тест 2 (Балансировка новых соединений)** и **Тест 7 (Передача трафика через OVS)**. Запускает 20 клиентов и проверяет, что Round Robin распределил их поровну (10/10). Дополнительно анализирует `ovs-ofctl dump-flows`, доказывая, что OVS обрабатывает трафик напрямую, а не передает каждый пакет контроллеру.
* **`tests/test3.sh`** — реализует **Тест 3 (Сохранение привязки)**, **Тест 4 (Изменение UDP-порта / NAT Rebinding)** и **Тест 5 (Маршрутизация по CID)**. Запускает клиента в режиме `-ChangePort`, проверяет, что порт изменился, но балансировщик по новому CID отправил клиента на исходный сервер. Также скрипт извлекает из логов CID до и после смены порта.
* **`tests/test4.sh`** — реализует **Тест 6 (Обработка некорректных пакетов)**. Отправляет в сеть случайный UDP-мусор, обрезанные заголовки и неверные CID, после чего проверяет, что контроллер не упал и корректно залогировал ошибку.

### Модульные тесты (парсер)

Отдельно реализованы юнит-тесты для проверки надежности парсера:
```bash
pytest controler/test_parser.py -v
```

*Эти тесты проверяют обработку Long/Short заголовков, случайного мусора, некорректных Configuration ID и неизвестных Server ID, а также маршрутизацию нескольких разных CID одного сервера.*

## Анализ ограничений

**1. Почему первый QUIC Initial нельзя маршрутизировать исключительно по серверному CID?**
Первый Initial-пакет содержит случайный CID, сгенерированный клиентом, так как клиент еще не знает, на какой сервер он попадет. В этом CID нет Server ID, поэтому балансировщик обязан принять решение самостоятельно (через Round Robin).

**2. Чем CID-based маршрутизация отличается от балансировки UDP по 5-tuple?**
Балансировка по 5-tuple (IP-адреса, порты и протокол) ломается при смене IP или порта клиентом (NAT Rebinding). Маршрутизация по CID сохраняет соединение, так как балансировщик смотрит на идентификатор соединения, который остается неизменным при смене сетевых параметров.

**3. Почему Short Header сложнее анализировать, чем Long Header?**
В Long Header есть явное поле длины DCID (Destination Connection ID Length). В Short Header длина CID не передается, она подразумевается известной из контекста (в нашем проекте используется жестко заданная длина 12 байт).

**4. Почему при смене CID балансировщик с таблицей ранее обнаруженных идентификаторов может потерять привязку?**
Если сервер выдал новый CID, stateful-балансировщик не найдет его в своей таблице и может применить Round Robin заново, отправив пакет на другой сервер. Наш механизм читает Server ID напрямую из нового CID.

**5. Почему разработанный механизм способен определить сервер по новому CID без хранения состояния?**
Потому что мы используем stateless-формат CID (`0xA1 | ServerID | Random`). Контроллеру достаточно прочитать второй байт, чтобы определить целевой сервер. Ему не нужно хранить историю выдачи CID.

**6. Какие ограничения накладывает использование обычных OpenFlow-правил, сопоставляющих пакеты по 5-tuple?**
OpenFlow не умеет заглядывать внутрь UDP-пейлоада (в QUIC-заголовки). Поэтому правила устанавливаются по 5-tuple после того, как контроллер распарсил CID. Такие правила не различают разные QUIC-соединения внутри одного UDP-потока.

**7. Что произойдет, если один UDP-поток будет использоваться для нескольких QUIC-соединений с различными CID?**
Так как OpenFlow-правила сопоставляют пакеты только по 5-tuple, все пакеты этого UDP-потока будут отправлены на тот сервер, который был выбран для первого соединения. Балансировка для остальных соединений в этом потоке работать не будет.

**8. Что произойдет с существующим QUIC-соединением при отказе выбранного сервера?**
Проект не реализует активный мониторинг (health checks) серверов. Если сервер упадет, существующее соединение оборвется.

**9. Какие недостатки безопасности и конфиденциальности имеет предложенный формат CID?**
Server ID передается в открытом виде. Злоумышленник или провайдер может проанализировать трафик и определить, к какому именно серверу идет обращение. Формат не обеспечивает криптографическую защиту маршрута.

**10. Какие изменения потребуются для реализации полноценного QUIC-LB без обращения к контроллеру для каждого нового UDP-потока?**
Потребуется шифрование CID (например, с помощью AES), чтобы скрыть Server ID. А для обработки трафика без участия контроллера необходим перенос логики расшифровки и маршрутизации на уровень коммутатора (SmartNIC) или использование P4-коммутаторов, умеющих парсить кастомные заголовки.
